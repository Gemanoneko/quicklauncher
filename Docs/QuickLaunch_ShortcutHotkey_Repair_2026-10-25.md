# Shortcut menus, upgraded Blender and hotkey recovery

Owner: Ender. Candidate: v1.104.3 on `codex/axis-resize`; baseline `8c4783ab5f28e3cc24fb398103e61755d86ce2f5` (v1.104.2). Source changes extend the existing tool. No visual, dependency or data-format changes.

## Evidence and causes

1. **Native shortcut menu error, verified.** The supplied 2026-10-22 screenshot shows the existing radial notice with the truncated CLR message `Value does not fall within the expected range.` `ShellMenu.cs` changed an AppsFolder alias into a desktop CLSID path before `SHParseDisplayName`. A hidden, no-window STA probe using the production COM declarations returned HRESULT `0x80070057` at that parse for every tested stored AppsFolder path. The original alias successfully parsed the current `blender.5.2` identity and Calculator and reached `IShellFolder.GetUIObjectOf`; a filesystem Notepad control also succeeded. The old `blender.5.1` ID failed as expected. No popup or application was opened. The helper returned the exception through `controller.popupTileMenu` and `region.js.openTileShellMenu` to the existing notice. Removing the rewrite repairs the failing Windows parser input.

2. **Upgrade leaves a stale identity, verified mechanism.** The live entry is now `shell:AppsFolder\blender.5.2` after Sergei re-added it. The removed entry cannot be recovered as historical evidence. The old ID `blender.5.1` is no longer parsable on this machine; the old launch handler nevertheless sent every stored shell URI straight to Explorer and ignored its result. This permits Explorer's Documents fallback instead of launching Blender. The new shared resolver reads current Start AppIDs before launch/menu, retains an existing exact identity, and replaces a missing versioned Blender ID only when exactly one versioned Blender identity exists. It changes only `path` on the same current stored item. ID, custom label/icon, arguments, region, order and concurrent unrelated changes survive. Missing/ambiguous IDs use existing errors and never reach Explorer; unrelated vendors and similar labels are never guessed. A catalog read failure uses existing `TARGET UNREADABLE` behavior. Filesystem shortcuts retain their original launch route and embedded arguments. Multiple installed Blender versions are deliberately ambiguous when the old ID has disappeared.

3. **Hotkey can get stuck, verified mechanisms; actual incident trigger unconfirmed.** A rejected/invalid rebind previously unregistered the working key first, while Manager retained the old setting and displayed it as bound. Registration is now replaced only after success; a transient startup conflict/lost registration is retried every five seconds for the configured key. A second path retained document-local rename/menu/drag/preview flags after reload, renderer loss or window destruction; `toggleForeground` then refused every press. A new radial document can begin with false extras without reporting a changed rename flag. Page invalidation now clears only that departed page's interaction state, cancels its tile gesture and closes its owned popup. Actual open menus, live gestures, rename work and outstanding shell operations continue to block reparenting. Blocked attempts are logged with their concrete state. The previously reviewed `WS_VISIBLE` fix is untouched.

The installed live EXE reports FileVersion `1.104.2`, ProductVersion `1.104.2.0` (read-only check). The historical successful 1.104.2 real-input QA does not certify today's intermittent symptom. A new away-window check is still needed to establish which trigger Sergei encountered and verify real Windows hotkey delivery and popup interaction. No real input, focus change, live profile write or QuickLaunch launch occurred during this diagnosis.
