# QuickLaunch native QA isolation — Store safety addendum

**Design verdict:** STORE SNAPSHOT EXTENSION ACCEPTED WITH BOUNDED CONTRACT; journal/native-move readiness remains unproved.

This addendum corrects the Store exclusion in the safety design committed at `68b13eab4a4d6bc377cb7dfca9a7e33e504258f7` (original design SHA256 `B1EB542A58C09D9993E7B7179673D776B805B5DCCA26ABC8B5E3A4C8C683CE3B`). Product code inspected through `git show 68b13ea:<path>` is unchanged from the original product baseline `91396260b4a127bcbb2546974f331c6f77841949`. This is a design ruling, not release clearance, behavior GO or native launch authorization. Inherited Codex model tier; legacy opus unavailable. No code, tests, application/native/system actions or git mutations were performed. The away window is expired.

## Broken boundary

Ender's STOP was correct. Store construction is not read-only: `src/main/store.js:135` calls `_load`; corrupt main can be quarantined at `:211`, recovery schedules `_save` at `:217`, and `_recheck` later re-enters `_load` at `:284`. Comparing Store data from index after construction cannot prevent those writes. Reading the seeds twice does not create an atomic filesystem transaction.

The minimum fix is an explicit optional constructor branch consuming already validated data, not a subclass whose virtual override runs unexpectedly during `super()`, and not a second ordinary Store read followed by comparison. Main/tmp/bak are all validated for the initial snapshot; "main-only" means main is the sole selected startup generation, not permission to ignore fallback files during validation.

## Additional owned files and accepted contract

Add only `src/main/store.js` and NEW `test/window/qa-isolation-store.test.js` to Ender's product scope. Existing scoped `src/main/qa-isolation.js`, index and focused tests perform the snapshot handoff. No generic Store rewrite, normal format/recovery change, file-delete logic, dependency/native launch or code outside the stated scope is authorized by this addendum.

1. The isolation validator/factory reads main/.tmp/.bak with read-only APIs after canonical confinement, regular-file/reparse/hard-link checks. Require all candidates safe and equivalent according to the committed isolation schema. Record bytes/hash and identity evidence. Return a deeply frozen, process-local validated snapshot plus immutable approved path/context; do not expose this capability through IPC, JSON flags or renderer data. Reject an incomplete/unvalidated QA constructor option before ordinary Store loading. Product factory validation must precede lock as required by the original design.

2. Store's optional QA branch validates its context/effective userData correspondence using only read-only operations and initializes data with a mutable deep clone of the immutable validated main snapshot. It must never call ordinary `_load`, `_defaults`, `_quarantine`, `_save`, recovery timers, or write/rename/copy APIs during construction. Initialize flags deliberately: no dirty state, no recheck timer, no read-only recovery state, initial generation evidence tied to the snapshot. Do not merge unsafe defaults into missing fields; require completeness in the validator. Normal no-option construction follows the existing code and preserves normal semantics.

3. A read-only freshness comparison immediately before constructor handoff is acceptable to reject observed changes, but never call it atomic. If comparison occurs inside the constructor, a refusal can mean one constructor entry; assert ZERO constructor mutations/native/global side effects. The stricter factory alternative keeps ZERO constructor entries for observed preconstruction refusals. Original zero-constructor requirement still applies to invalid arguments/paths/seeds caught in the early validator. Do not waive zero writes, quarantines, timers, lock-before-validation or native effects.

4. Disk changes after snapshot capture cannot change startup runtime data: Store does not reread candidates in QA. On QA `_load`, `_recheck`, `recheck`, focus/timer or explicit recovery entry, do not invoke normal recovery, quarantine or defaults; return the safe owned state or a deterministic refused result. Store memory remains mutable for ordinary QA UI changes, but the context/source snapshot is immutable and independent of it. Global autostart/hotkey/updater/launch guards from the original design remain mandatory even if in-memory settings are altered unexpectedly.

5. Before accepting QA `set`/renderer updates and before flush, validate the whole resulting state with the QA predicate: safe settings, region ownership and fixture-confined app/path/origin data. Validation failure leaves previous safe memory intact, cancels any pending save/recheck timers, reports an isolation error and refuses persistence. In-place mutation through `get()` is possible with the present API; therefore flush must revalidate full memory and cannot rely only on guarded setters. No unsafe staged state is serialized.

6. QA persistence may use the existing durable save algorithm only after read-only canonical/path/identity checks for profile and every store target; unsafe/ambiguous target refuses before `_writeDurable` or `_rotateBackup`. Do not read external .bak through ordinary `_rotateBackup` fallback logic. Match the latest generation that this QA instance itself wrote, not the original prelaunch hashes forever: successful writes update its expected generations, while unexpected disk changes refuse. Missing candidates after a failed owned durable write are handled as a QA persistence failure, never normal startup recovery. Cancel timers and fail closed; do not retry through ordinary `_load` or copy/quarantine a suspicious file.

7. The resulting guarantee is precise: observed invalid input/drift produces no Store mutation; runtime boot data comes exclusively from a validated snapshot; no ordinary Store recovery side effects occur in QA; actual writes are limited to the approved owned profile while its validated filesystem identities remain intact. Rechecking path/identity immediately before a pathname write is useful but is NOT proof against an active external actor swapping junctions/links between check and open/rename. Do not claim a race-free or OS-enforced filesystem boundary from these APIs. Strong protection against concurrent path substitution would require a separately reviewed handle/OS containment design. Native readiness must report this limitation and STOP if the owned profile cannot be established as quiescent or any drift is observed; this addendum does not authorize that stronger implementation.

## Independent journal state: Store snapshot is insufficient

`src/main/moves/journal.js` `Journal.load()` rereads `moves-journal.json` and renames a malformed file to `.corrupt-*`. `Mover` constructs its own Journal; `Mover.init()` loads it asynchronously and `_reconcile()` inspects src/dst, commits Store changes and calls `journal.finish`, which appends `moves-log.jsonl` and writes/renames journal/.tmp. Its `_originFromLog` independently rereads history. Controller creates/starts this mover outside Store construction. Existing fixture confinement protects move operations but does not convert journal reads/writes into the immutable Store snapshot boundary.

A fresh or empty prechecked journal alone does not prove zero journal quarantine/write under replacement races. Store read-only mode also does not prevent journal.finish or Journal quarantine. Invalid journal app paths can be read and used for reconciliation before Store rejects a later commit. Do not claim this Store extension clears native file-move acceptance.

Within the existing index scope, a bounded initial UI phase can avoid initializing Mover by supplying an unavailable moveSetup (the existing unavailable path is not native move PASS). Confirm actual controller behavior with fakes; no journal load/write may occur. This phase can prove Manager/layout/tray isolation but cannot clear move tests. Do not silently substitute it for full acceptance or globally remove moves.

For native move readiness, STOP and obtain a separately committed exact-file brief for a snapshot/guard handoff across `src/main/regions/controller.js`, `src/main/moves/mover.js` and `src/main/moves/journal.js` plus focused tests. Minimum future contract: validated immutable empty initial journal/history or validated pending records; no disk quarantine/fallback during QA load; no independent unvalidated history import; fixture-confined recovery state; validated current owned journal/.tmp/log targets before each write; error propagation that disables/refuses mover rather than logging and continuing; no unsafe native move after a journal guard failure. This is NOT authorized implementation scope in this addendum. A validator-only assertion is insufficient evidence.

### Proposed separate stage B: bounded journal snapshot handoff

The following design is feasible for a fresh native acceptance session and is recommended for a separately authorized Ender stage. It does not certify prior pending-journal recovery cases.

- Exact extra product files: `src/main/regions/controller.js`, `src/main/moves/mover.js`, `src/main/moves/journal.js`; NEW `test/regions/qa-isolation-journal.test.js` and NEW `test/regions/qa-isolation-mover.test.js`. Extend already scoped validator/index/isolation tests to cover all consumers. No native binding, file-move algorithm, schema or normal recovery rewrite.
- The early validator also records absence or canonical regular-file identity/hash for journal, journal.tmp and log. For this stage, require fresh empty pending journal and empty/absent history; reject pending/malformed records, unexpected .tmp and external/link targets. The snapshot contains explicitly validated empty entries/history, not an absent-field instruction to read disk later. Seeded moved/orphan fixture scenes are still allowed if all apps/origins/files are fixture-confined; recovery of a previous interrupted run is separate scope.
- Index passes the immutable context to Controller; Controller passes it to Mover; Mover passes it to Journal. QA `Journal.load` consumes the snapshot and never disk rereads/quarantines. QA Mover starts from those empty entries, so startup `_reconcile` makes no journal or Store writes. Normal construction/load/reconcile remains exactly the normal branch.
- QA history lookup uses captured initial history plus records successfully appended by this instance, maintained in Journal memory; `_originFromLog` must not read unvalidated disk history. Appending maintains the normal record semantics, and failure must not claim a record was durably added. Returning invented origin or silently discarding prior-history acceptance is not allowed.
- Before each journal intent/update/finish/note write, validate confinement and identity of journal/.tmp/log/profile, source/destination/origin state and expected own generations. Invalid drift latches the QA mover unavailable, rejects the operation and cannot be swallowed by `_journalQuietly` into continuing a native move. Revalidate the latched state immediately before `_move`, including rollback; never escape the fixture as an error recovery. A guarded write failure keeps existing normal durable intent/error semantics within the fixture; do not unlink/overwrite an unproved target or retry through disk recovery.
- Controller's asynchronous init error handling must record isolation failure and leave mover unavailable; logging alone is insufficient. IPC must report refused/unavailable instead of claiming success. Native operations cannot begin while init is pending or after a guard fault, even when callbacks are invoked directly.
- Tests use actual Journal/Mover/Controller modules with recording fsp/win32 and throw-on-side-effect fakes: snapshot valid but disk corrupt before load gives zero quarantine/reread; malformed prevalidation refuses before windows; empty startup creates no journal writes; own add/back/adopt/orphan operations preserve expected records and confine src/dst; unsafe history/pending record/link/drift refuses; async init and append failure disables mover; callbacks/rollback after fault perform zero native operations. Normal journal recovery tests remain passing. No test may move actual files outside the named scratch fixture.

Stage B shares the explicit pathname TOCTOU limitation in Store contract item 7. Neither snapshot handoff nor a generation guard is OS-enforced protection against hostile concurrent root replacement. Any observed drift or inability to establish quiescent owned fixture/profile is a STOP, not proof by assumption. A full native acceptance claim remains blocked until this separate stage is implemented, committed, independently reviewed and its packaged source correspondence is proven.

## Required focused tests (recording fakes only)

- Actual Store QA constructor consumes the snapshot even when disk read candidates subsequently become corrupt/missing/locked or unsafe. Set ordinary `_load`, `_defaults`, `_quarantine`, recovery timers and every write/copy/rename API to throw if constructor reaches them. Constructor must not reach them. Invalid context/effective path must reject without mutation; count constructor entries separately from side-effect count.
- Validator observes altered/missing/unreadable/linked candidate before handoff: refuses before factory construction and lock. Snapshot is deeply frozen; Store mutation cannot mutate it; mutation of original parsed input cannot mutate runtime data. Do not label this simulated sequential race as atomic proof.
- Actual QA recheck/focus/load paths do not import later unsafe disk data, call defaults/quarantine or schedule recovery. Actual normal-mode missing/corrupt/locked recovery remains unchanged in existing Store tests.
- QA safe state changes and repeated successful durable saves update expected own generation metadata. Unexpected main/tmp/bak/profile identity/hash drift, linked targets, ambiguous read or write failure refuses persistence; pending timers canceled; no rotation/quarantine/copy/recovery fallback occurs after refusal. Include interrupted owned-write state and ensure flush reports failure rather than successful durability.
- Direct mutation via `get()` to unsafe hotkey/autostart/app/origin is caught at flush before any writer. Renderer setter refusal retains prior state. Global side-effect route tests remain mandatory independently of Store guards.
- No-move phase uses actual controller wiring with recording Journal/native fakes to prove zero journal initialization/reconciliation and zero move effects. Missing proof means this phase also remains unready. Full journal/native-move acceptance explicitly stays pending.
